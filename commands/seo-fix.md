You are running **/seo-fix**: take this site as far toward 10/10 as its code allows,
safely, and prove every step with measurements. You are the implementation team,
not an auditor -- the scanner finds the problems, you fix them, the scanner confirms.

Target and options: $ARGUMENTS

- No target -> the current working directory. A path -> that project.
- A URL **and no codebase** -> fix-pack mode (step 8): nothing is edited.
- `--dry-run` -> steps 0-3 only: scorecard and plan, no edits.
- `--yes` -> non-interactive (CI, headless): never ask. Apply `auto` items, and
  `input` items only when every fact they need was found with confidence `found`.
  Skip `review` items and anything needing a missing fact; list them in the report.
  **If you cannot ask the user a question in this session, behave as `--yes`.**
- `--only id,id` -> restrict the run to those check IDs.
- `key=value` pairs (`site_url=https://client.com brand="Client Co" og_image=public/og.png
  icon=public/favicon.ico`) -> facts supplied by the user. They count as confirmed,
  so `--yes` can use them; they win over anything `detect` found.
- `approve=id,id` (e.g. `approve=next-image,robots-search-open`) -> those `review`
  items are approved in advance. Nothing else is: every other `review` item is still
  skipped under `--yes` and asked about otherwise.

## 1. Safety baseline

Run `git -C <target> status --porcelain`.

- **Not a git repository:** every edit would be unreviewable and unrevertable. Ask
  the user to allow `git init && git add -A && git commit -m "Baseline before
  seo-fix"` first. Under `--yes`, stop and report -- never edit an untracked tree
  unattended.
- **Uncommitted changes present:** note the files. Never modify, stage, stash or
  revert them; if a fix must touch one of those files, touch only the lines the fix
  needs and say so in the report.

## 2. Detect

`python3 <SCAN> detect <target>` gives the stack, the implementation reference, the
render recipe (how to get the real HTML) and the facts it found. Read the
implementation reference it names (`nextjs-implementation.md`,
`react-spa-implementation.md`, `cms-implementation.md`, or the playbook itself).

## 3. Baseline score -- from rendered output whenever possible

**Save the baseline before the first edit** -- the before/after comparison is the
deliverable, and a baseline taken after an edit measures nothing. (If edits already
exist without one, never stash, reset or revert to get it: score the committed state
from a `git worktree add` copy of HEAD, or report the after-score alone and say why.)
Rendered HTML is the evidence; the source scan only says where to look.

1. **Dependencies.** If the recipe says to install and `node_modules` is missing,
   ask once (`npm ci` when a lockfile exists -- it does not rewrite the lockfile).
   Under `--yes`, install with `npm ci`/`pnpm install --frozen-lockfile`/`yarn
   install --frozen-lockfile` only when a lockfile exists; otherwise go source-only.
2. **Build** with the project's own script. **If the build fails before you have
   changed anything,** that is a pre-existing defect: record the error, do not fix
   unrelated code, and continue source-only.
3. **Score and save the baseline** with the recipe's evidence flag:
   `python3 <SCAN> score <target> --html <outdir> --save` or
   `python3 <SCAN> score <target> --serve "<start cmd>" --url http://localhost:<port> --save`
   (`--serve` starts the server, scans, and always stops it -- never leave a server
   running between tool calls). Static HTML needs neither flag.

The scorecard's **Fix plan** is your work list: `auto`, `input` (with the facts it
needs), `review`. `--dry-run` ends here: present the scorecard and the plan.

## 4. One round of questions (skip entirely under `--yes`)

Ask everything in **one** message (use AskUserQuestion when available):

- **Facts** the `input` items need -- show each value `detect` found and its source
  for confirmation, and ask for the missing ones. `site_url` and `brand` matter most.
  Never guess a production domain from a preview deployment.
- **Approvals** for `review` items not already listed in `approve=` -- one line each:
  what changes and what it risks (e.g. "robots.txt blocks all search engines -- remove
  the blanket Disallow?"). Default is *not approved*.

Then do not ask again. Anything still unknown is reported, not guessed.

## 5. Fix

Work the plan in the playbook's order of operations (`base-url` before canonicals,
`schema-valid` before `schema-org`, root defaults before per-page values). For each
check:

1. Read the files under **Where to fix** and confirm the finding.
2. Apply the playbook recipe for this stack, in the codebase's own style. Check new
   titles and descriptions before writing them: `python3 <SCAN> len "<title>" "<description>"`.
3. Log it: check ID -> files -> one-line summary.

Non-negotiable:

- **No invented facts.** Titles, descriptions, alt text and llms.txt summaries are
  written from each page's own content. Addresses, phones, prices, ratings, authors,
  dates, logos and social profiles come only from the codebase or the user.
- **Source, not output.** Never edit `dist/`, `out/`, `.next/`, `_site/`, or any
  other build output (static-HTML sites excepted -- there the HTML is the source).
- **Same look.** No visual changes; no refactors beyond what a fix needs.
- **Data-driven pages stay data-driven.** Blog posts, products and docs get their
  metadata and JSON-LD from the template/`generateMetadata`, not per-page hand edits.
- **Structural items only when approved** (`server-rendered`, `next-image`,
  robots changes) -- and one at a time, verified before moving on.

## 6. Verify -- until the numbers agree

1. Run the project's own checks that exist: typecheck (`tsc --noEmit` when there is
   a `tsconfig.json`), `lint`, `test`, then the build. A failure your change caused
   is yours: fix it or revert that item. Never finish on a broken build.
2. Re-score with the same evidence flag plus `--compare`:
   `python3 <SCAN> score <target> <evidence flags> --compare`
3. Every check you worked on should now pass. For each that does not: read the
   rendered page the scanner cites, find out why, fix, re-verify. Up to three rounds;
   then report it as blocked, with the reason.
4. `REGRESSIONS` in the compare output must be fixed before you finish.
5. `git -C <target> diff --stat` -- every changed file should be one you meant to change.

## 6b. Commit only on request

Do not commit, push or open a PR unless the user asks. Offer a commit message:
`SEO: <score before> -> <score after>/10 -- <top 3 fixes>`.

## 8. Fix-pack mode (URL, no codebase)

No code means nothing to edit. Follow the playbook's *Live site, no code access*
section:

1. `python3 <PROBE> preflight <url>` -- exit 3 means this environment's network
   policy blocks the host: stop and relay the remedy the probe prints. Never produce
   a fix pack from remembered facts.
2. `python3 <SCAN> score <url> -n 25 --save` for the scorecard and the page table.
3. Write `seo-fix-pack/<domain>/` (README with platform-specific steps, robots.txt
   merged with the live one, llms.txt, homepage JSON-LD, `meta/pages.csv` with
   proposed titles and descriptions written from each page's content).
4. Report the current score, the score the pack should reach
   (`score_after_fixable`), and that it becomes real only when the client applies it
   -- re-run `/seo-fix <url>` afterwards to measure.
